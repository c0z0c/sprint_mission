## 1. 개요

### 1.1. Hugging Face 자동 로딩 메커니즘

Hugging Face의 `datasets` 라이브러리는 특정 파일 구조와 명명 규칙을 따르면 별도의 코딩 없이 자동으로 데이터를 로딩합니다. 이 메커니즘(mechanism)은 파일 익스텐션(extension)과 파일명을 분석하여 적절한 리더(reader)를 선택하고, 데이터를 파이토치(PyTorch) 텐서나 넘파이(NumPy) 배열로 변환합니다.

자동 로딩의 핵심 원리는 컨벤션 오버 컨피규레이션(Convention over Configuration) 패러다임(paradigm)입니다. 개발자가 명시적으로 설정을 작성하는 대신, 표준화된 규칙을 따르면 시스템이 자동으로 올바른 동작을 수행합니다. 이 접근법은 데이터 과학자들이 모델 개발에 집중할 수 있도록 인프라스트럭처(infrastructure) 설정의 복잡성을 제거합니다.

자동 로딩은 다음 과정을 거칩니다. 먼저 파일 익스텐션을 확인하여 데이터 포맷을 식별합니다. 다음으로 파일명에서 스플릿(split) 키워드를 추출하여 데이터를 학습, 검증, 테스트 세트로 구분합니다. 마지막으로 각 파일을 읽어 데이터셋 딕셔너리(dictionary) 객체로 조립합니다.

### 1.2. 파일 기반 데이터셋의 장점

파일 기반 접근법은 여러 이점을 제공합니다. 첫째, 버전 컨트롤(control) 시스템과의 통합이 용이합니다. 깃(Git)과 같은 툴로 데이터셋의 변경 이력을 추적할 수 있으며, 브랜치(branch)를 통해 실험적 변경을 안전하게 테스트할 수 있습니다. 깃 LFS(Large File Storage)를 사용하면 대용량 파일도 효율적으로 관리할 수 있습니다.

둘째, 데이터베이스나 외부 서비스 없이도 로컬 환경에서 즉시 작업을 시작할 수 있습니다. 네트워크 의존성이 없어 오프라인 환경에서도 개발이 가능하며, 데이터 접근 속도가 빠릅니다. 셋째, 클라우드 스토리지나 CDN(Content Delivery Network)에 쉽게 배포할 수 있어 협업과 공유가 간편합니다.

넷째, 파일 시스템 기반이므로 표준 유닉스(Unix) 도구들을 활용할 수 있습니다. `grep`, `awk`, `sed` 같은 명령어로 데이터를 빠르게 검색하고 조작할 수 있습니다. 다섯째, 재현성(reproducibility)이 높습니다. 특정 버전의 파일을 체크아웃(checkout)하면 정확히 동일한 데이터로 실험을 재현할 수 있습니다.

## 2. 기본 폴더 구조

### 2.1. 단일 태스크 구조

가장 기본적인 구조는 루트 디렉토리(directory)에 스플릿별 파일을 배치하는 방식입니다. 이 구조는 단일 태스크나 단일 도메인(domain)의 데이터를 다룰 때 적합합니다.

```
my_dataset/
├── train.jsonl
├── validation.jsonl
├── test.jsonl
└── README.md
```

이 구조에서 Hugging Face는 파일명에서 자동으로 `train`, `validation`, `test` 스플릿을 인식합니다. 각 `.jsonl` 파일은 줄바꿈으로 구분된 JSON 오브젝트(object)의 시퀀스(sequence)입니다. README.md 파일은 데이터셋에 대한 설명과 사용법을 담고 있으며, Hugging Face Hub에서 데이터셋 카드로 자동 렌더링(rendering)됩니다.

단일 태스크 구조의 장점은 단순성입니다. 파일 세 개만 있으면 즉시 학습을 시작할 수 있으며, 관리와 유지보수가 쉽습니다. 소규모 프로젝트나 프로토타이핑(prototyping) 단계에서 특히 유용합니다.

### 2.2. 다중 컨피규레이션 구조

하나의 데이터셋에서 여러 태스크나 변형(variant)을 지원해야 할 때는 서브디렉토리(subdirectory)를 활용합니다. 각 서브디렉토리는 독립적인 컨피규레이션(configuration)으로 취급됩니다.

```
my_dataset/
├── default/
│   ├── train.jsonl
│   ├── validation.jsonl
│   └── test.jsonl
├── augmented/
│   ├── train.jsonl
│   └── validation.jsonl
├── balanced/
│   ├── train.jsonl
│   ├── validation.jsonl
│   └── test.jsonl
└── README.md
```

예를 들어, `default` 컨피규레이션은 원본 데이터를 포함하고, `augmented`는 데이터 증강(augmentation)이 적용된 버전을, `balanced`는 클래스 밸런싱(balancing)이 적용된 버전을 포함할 수 있습니다. 로딩 시 `name` 파라미터(parameter)로 원하는 컨피규레이션을 선택할 수 있습니다.

다중 컨피규레이션 구조는 A/B 테스팅이나 하이퍼파라미터(hyperparameter) 실험에 유용합니다. 서로 다른 전처리(preprocessing) 방법을 적용한 여러 버전을 유지하면서, 각각의 성능을 비교할 수 있습니다.

### 2.3. 파일 명명 규칙

Hugging Face가 자동으로 인식하는 파일명 패턴(pattern)은 다음과 같습니다. 정확한 명명 규칙을 따르면 추가 설정 없이 데이터가 올바른 스플릿으로 자동 분류됩니다.

**스플릿 자동 인식 키워드:**
- `train`, `training` → 학습 데이터
- `validation`, `valid`, `val`, `dev` → 검증 데이터
- `test`, `testing`, `eval` → 테스트 데이터

**허용되는 파일 형식:**
- `.jsonl` 또는 `.json` (JSON Lines 또는 JSON 배열)
- `.csv`, `.tsv` (테이블 형식 데이터)
- `.parquet` (컬럼나(columnar) 저장 포맷)
- `.arrow` (아파치 애로우 포맷)
- `.txt` (텍스트 파일, 한 줄이 하나의 샘플)

**파일명 예시:**
- `train.jsonl` - 표준 학습 데이터
- `train-00000.jsonl`, `train-00001.jsonl` - 샤딩(sharding)된 파일
- `validation_ko.jsonl` - 언어 식별자(identifier) 포함
- `test_clean.jsonl` - 버전 식별자 포함
- `dev-2024.jsonl` - 날짜 정보 포함

샤딩된 파일은 대용량 데이터셋을 여러 파일로 분할할 때 사용됩니다. Hugging Face는 동일한 접두사(prefix)를 가진 파일들을 자동으로 병합(merge)하여 하나의 스플릿으로 처리합니다. 파일명에 추가 정보를 포함할 수 있지만, 스플릿 키워드는 반드시 포함되어야 합니다.

## 3. JSONL 스키마 by 태스크

### 3.1. 인스트럭션 튜닝 (챗봇/어시스턴트)

인스트럭션 튜닝(instruction tuning)은 모델이 사용자의 지시를 이해하고 적절히 응답하도록 학습시키는 방법입니다. 스키마(schema)는 입력 프롬프트(prompt)와 기대되는 출력을 명확히 구분합니다. 이 방법은 알파카(Alpaca), 비쿠냐(Vicuna) 같은 오픈소스 모델 학습에 널리 사용됩니다.

**스키마:**
```json
{
  "instruction": "사용자의 요청이나 질문",
  "input": "추가 컨텍스트 (선택적)",
  "output": "모델이 생성해야 할 응답"
}
```

`instruction` 필드는 모델에게 수행할 작업을 지시합니다. `input` 필드는 선택적이며, 작업에 필요한 추가 정보를 제공합니다. 예를 들어 번역 태스크에서 `instruction`은 "다음 텍스트를 영어로 번역하세요"이고, `input`은 번역할 원문입니다. `output` 필드는 모델이 생성해야 할 정답입니다.

**train.jsonl 예시:**
```json
{"instruction": "다음 텍스트를 한 문장으로 요약해주세요.", "input": "인공지능은 인간의 학습능력, 추론능력, 지각능력을 인공적으로 구현하려는 컴퓨터 과학의 한 분야입니다.", "output": "인공지능은 인간의 지능을 컴퓨터로 구현하는 기술입니다."}
{"instruction": "파이썬으로 피보나치 수열의 n번째 항을 구하는 함수를 작성해주세요.", "input": "", "output": "재귀를 사용한 구현입니다: def fibonacci(n): return n if n <= 1 else fibonacci(n-1) + fibonacci(n-2)"}
{"instruction": "기후 변화의 주요 원인 3가지를 설명해주세요.", "input": "", "output": "1) 화석 연료 연소로 인한 온실가스 배출 2) 삼림 벌채로 인한 탄소 흡수원 감소 3) 산업 활동으로 인한 메탄 및 이산화질소 배출입니다."}
{"instruction": "다음 이메일을 공손한 어조로 다시 작성해주세요.", "input": "빨리 답장 안 주면 다른 업체로 갈 거예요.", "output": "빠른 시일 내에 회신 주시면 감사하겠습니다. 일정상 다른 옵션도 검토 중이오니 양해 부탁드립니다."}
{"instruction": "머신러닝과 딥러닝의 차이를 초보자가 이해할 수 있게 설명해주세요.", "input": "", "output": "머신러닝은 컴퓨터가 데이터로부터 패턴을 학습하는 전체 기술이고, 딥러닝은 뇌의 신경망을 모방한 특별한 머신러닝 방법입니다. 딥러닝은 더 복잡한 패턴을 인식할 수 있지만 많은 데이터가 필요합니다."}
```

인스트럭션 튜닝 데이터는 다양성이 중요합니다. 코딩, 요약, 번역, 창작 등 여러 카테고리(category)의 태스크를 포함하면 모델의 범용성이 향상됩니다. 각 샘플의 `output`은 고품질이어야 하며, 사실적 정확성과 언어적 자연스러움을 모두 갖춰야 합니다.

### 3.2. 대화형 멀티턴

멀티턴(multi-turn) 대화는 여러 번의 주고받기가 있는 대화를 모델링합니다. 컨텍스트 윈도우(context window) 내에서 이전 대화를 기억하고 맥락에 맞는 응답을 생성해야 합니다. 챗봇이나 대화형 어시스턴트를 만들 때 필수적인 데이터 포맷입니다.

**스키마:**
```json
{
  "messages": [
    {"role": "user", "content": "사용자 메시지"},
    {"role": "assistant", "content": "어시스턴트 응답"},
    {"role": "user", "content": "후속 질문"},
    {"role": "assistant", "content": "맥락을 고려한 응답"}
  ]
}
```

`messages` 배열은 대화의 전체 흐름을 담습니다. 각 메시지는 `role`과 `content`를 가지며, `role`은 `user` 또는 `assistant`입니다. 일부 시스템에서는 `system` 롤도 사용하여 모델의 행동 지침을 제공합니다.

**train.jsonl 예시:**
```json
{"messages": [{"role": "user", "content": "파이썬으로 리스트의 평균을 구하는 방법을 알려주세요."}, {"role": "assistant", "content": "sum(list) / len(list)를 사용하시면 됩니다."}, {"role": "user", "content": "빈 리스트일 때는 어떻게 처리하나요?"}, {"role": "assistant", "content": "len(list)가 0일 때 division by zero 에러가 발생하므로 if문으로 확인해야 합니다: return sum(list) / len(list) if len(list) > 0 else 0"}]}
{"messages": [{"role": "user", "content": "오늘 저녁 메뉴 추천해주세요."}, {"role": "assistant", "content": "날씨가 쌀쌀하니 따뜻한 김치찌개는 어떠세요?"}, {"role": "user", "content": "채식주의자인데요."}, {"role": "assistant", "content": "그렇다면 두부김치나 된장찌개를 추천드립니다. 버섯을 많이 넣으면 더 풍미가 좋습니다."}]}
```

### 3.3. 텍스트 분류

텍스트 분류(text classification)는 주어진 텍스트를 미리 정의된 카테고리로 분류하는 태스크입니다. 라벨(label)은 정수 인덱스(index)나 문자열로 표현할 수 있습니다. 감정 분석, 스팸 필터링, 주제 분류 등 다양한 응용 분야가 있습니다.

**스키마:**
```json
{
  "text": "분류할 텍스트",
  "label": "카테고리 이름 또는 인덱스"
}
```

`text` 필드는 분류 대상이 되는 입력 텍스트입니다. `label` 필드는 해당 텍스트의 카테고리를 나타냅니다. 문자열 라벨을 사용하면 가독성이 좋고, 정수 라벨을 사용하면 메모리 효율이 높습니다.

**train.jsonl 예시:**
```json
{"text": "이 영화는 정말 재미있고 감동적이었습니다. 강력 추천합니다!", "label": "positive"}
{"text": "배송이 너무 늦고 제품 상태도 좋지 않았습니다.", "label": "negative"}
{"text": "가격 대비 괜찮은 것 같아요. 그냥 보통입니다.", "label": "neutral"}
{"text": "딥러닝 모델의 하이퍼파라미터 튜닝에 대한 논문입니다.", "label": "technology"}
{"text": "중앙은행이 기준금리를 0.25%p 인상했습니다.", "label": "economy"}
{"text": "국가대표팀이 월드컵 본선 진출에 성공했습니다.", "label": "sports"}
{"text": "새로운 항생제가 임상시험에서 높은 효과를 보였습니다.", "label": "science"}
```

텍스트 분류 데이터셋을 구성할 때는 클래스 밸런스를 고려해야 합니다. 한 클래스의 샘플이 지나치게 많으면 모델이 편향(bias)될 수 있습니다. 각 클래스당 최소 수백 개 이상의 샘플을 확보하는 것이 좋습니다.

### 3.4. 요약

요약(summarization) 태스크는 긴 텍스트를 핵심 정보만 포함하는 짧은 버전으로 압축합니다. 추상적 요약(abstractive summarization)은 새로운 문장을 생성하고, 추출적 요약(extractive summarization)은 원문에서 중요한 문장을 선택합니다.

**스키마:**
```json
{
  "document": "원본 긴 텍스트",
  "summary": "요약된 텍스트"
}
```

`document` 필드는 요약할 원문이며, 보통 여러 문장 또는 여러 문단으로 구성됩니다. `summary` 필드는 원문의 핵심 내용을 담은 짧은 텍스트입니다. 좋은 요약은 정보성(informativeness)과 간결성(conciseness)의 균형을 맞춥니다.

**train.jsonl 예시:**
```json

{"document": "기후변화는 21세기 인류가 직면한 가장 큰 도전 과제입니다. 산업혁명 이후 화석연료 사용 증가로 대기 중 이산화탄소 농도가 급증했고, 이로 인해 지구 평균 기온이 상승하고 있습니다. 해수면 상승, 극단적 기상 현상 증가, 생태계 파괴 등의 문제가 발생하고 있으며, 이를 해결하기 위해 국제사회는 파리기후협약을 체결하고 탄소중립 목표를 설정했습니다. 재생에너지 전환과 에너지 효율 개선이 시급합니다.", "summary": "화석연료로 인한 기후변화가 심각해지면서 국제사회는 탄소중립과 재생에너지 전환을 추진하고 있습니다."}
{"document": "양자컴퓨터는 기존 컴퓨터와 근본적으로 다른 원리로 작동합니다. 클래식 비트 대신 큐비트를 사용하며, 중첩과 얽힘이라는 양자역학적 현상을 활용합니다. 이를 통해 특정 문제들을 기존 슈퍼컴퓨터보다 기하급수적으로 빠르게 해결할 수 있습니다. 현재는 노이즈와 오류율이 높아 실용화에 한계가 있지만, IBM, 구글, 마이크로소프트 등이 양자 우위를 입증하기 위해 경쟁하고 있습니다.", "summary": "양자컴퓨터는 큐비트와 양자역학을 활용해 특정 문제를 빠르게 해결하지만, 아직 실용화를 위해 기술 개선이 필요합니다."}
```

요약 데이터를 만들 때는 압축 비율(compression ratio)을 고려해야 합니다. 일반적으로 원문의 20-30% 길이가 적절하며, 너무 짧으면 정보 손실이 크고 너무 길면 요약의 의미가 없습니다. 요약문은 원문의 핵심 메시지를 정확히 전달해야 합니다.

### 3.5. 질의응답 (QA)

질의응답(question answering) 시스템은 주어진 컨텍스트에서 질문에 대한 답을 추출하거나 생성합니다. 스쿼드(SQuAD) 포맷이 가장 널리 사용되며, 기계 독해(machine reading comprehension) 능력을 평가하는 표준 벤치마크입니다.

**스키마 (추출형):**
```json
{
  "context": "답변의 근거가 되는 문단",
  "question": "질문",
  "answer": "답변 텍스트",
  "answer_start": "컨텍스트 내 답변 시작 위치 (선택적)"
}
```

`context` 필드는 답변을 찾을 수 있는 근거 텍스트입니다. `question`은 사용자의 질문이며, `answer`는 컨텍스트에서 추출한 정답입니다. `answer_start`는 답변이 컨텍스트에서 시작되는 문자 인덱스로, 추출형 QA에서 중요한 정보입니다.

**train.jsonl 예시:**
```json
{"context": "트랜스포머는 2017년 구글이 발표한 딥러닝 모델 아키텍처입니다. 어텐션 메커니즘만으로 구성되어 있으며 RNN이나 CNN을 사용하지 않습니다.", "question": "트랜스포머는 언제 발표되었나요?", "answer": "2017년", "answer_start": 11}
{"context": "파이썬은 귀도 반 로섬이 개발한 고급 프로그래밍 언어입니다. 문법이 간결하고 읽기 쉬워 초보자들이 배우기 좋습니다. 다양한 라이브러리가 있어 데이터 과학, 웹 개발, 자동화 등에 널리 사용됩니다.", "question": "파이썬의 개발자는 누구인가요?", "answer": "귀도 반 로섬", "answer_start": 5}
{"context": "BERT는 Bidirectional Encoder Representations from Transformers의 약자로, 2018년 구글이 공개한 사전학습 언어 모델입니다. 마스크드 언어 모델링과 다음 문장 예측 두 가지 태스크로 사전학습됩니다.", "question": "BERT의 사전학습 방법은 무엇인가요?", "answer": "마스크드 언어 모델링과 다음 문장 예측", "answer_start": 89}
{"context": "GPU는 Graphics Processing Unit의 약자로 원래 그래픽 렌더링을 위해 개발되었습니다. 하지만 병렬 연산에 특화되어 있어 딥러닝 학습에도 활용됩니다. NVIDIA의 CUDA 플랫폼이 대표적입니다.", "question": "GPU가 딥러닝에 적합한 이유는?", "answer": "병렬 연산에 특화되어 있어", "answer_start": 67}
```

QA 데이터셋은 질문의 다양성과 난이도 분포가 중요합니다. 단순한 사실 확인 질문부터 추론이 필요한 복잡한 질문까지 포함하면 모델의 이해력이 향상됩니다. 답변은 컨텍스트에서 직접 찾을 수 있어야 하며, 모호하지 않아야 합니다.

### 3.6. 번역

기계 번역(machine translation) 태스크는 소스 언어의 텍스트를 타겟 언어로 변환합니다. 언어 코드를 명시하면 다국어 데이터셋 관리가 용이하며, 단일 모델로 여러 언어 쌍을 처리할 수 있습니다.

**스키마:**
```json
{
  "source": "원문 텍스트",
  "target": "번역 텍스트",
  "source_lang": "원문 언어 코드 (선택적)",
  "target_lang": "타겟 언어 코드 (선택적)"
}
```

`source`와 `target` 필드는 각각 원문과 번역문을 담습니다. `source_lang`과 `target_lang`은 ISO 639-1 언어 코드를 사용하는 것이 표준입니다. 예를 들어 한국어는 `ko`, 영어는 `en`, 일본어는 `ja`입니다.

**train.jsonl 예시:**
```json
{"source": "Machine learning is a subset of artificial intelligence.", "target": "머신러닝은 인공지능의 하위 분야입니다.", "source_lang": "en", "target_lang": "ko"}
{"source": "딥러닝 모델을 학습시키려면 많은 데이터가 필요합니다.", "target": "Training deep learning models requires a lot of data.", "source_lang": "ko", "target_lang": "en"}
{"source": "Natural language processing enables computers to understand human language.", "target": "자연어 처리는 컴퓨터가 인간의 언어를 이해할 수 있게 합니다.", "source_lang": "en", "target_lang": "ko"}
{"source": "트랜스포머 아키텍처는 번역 품질을 크게 향상시켰습니다.", "target": "The transformer architecture has greatly improved translation quality.", "source_lang": "ko", "target_lang": "en"}
{"source": "Attention mechanisms allow models to focus on relevant parts of the input.", "target": "어텐션 메커니즘은 모델이 입력의 관련 부분에 집중할 수 있게 합니다.", "source_lang": "en", "target_lang": "ko"}
```

번역 데이터의 품질은 유창성(fluency)과 충실성(fidelity)으로 평가됩니다. 유창성은 번역문이 자연스러운 타겟 언어로 작성되었는지를, 충실성은 원문의 의미를 정확히 전달하는지를 나타냅니다. 양방향 번역 쌍을 포함하면 모델의 언어 이해도가 향상됩니다.

### 3.7. 감성 분석

감성 분석(sentiment analysis)은 텍스트에 담긴 감정이나 의견의 극성(polarity)을 판단합니다. 이진 분류(긍정/부정)나 다중 클래스 분류(매우 긍정, 긍정, 중립, 부정, 매우 부정)로 구현됩니다. 고객 리뷰 분석, 소셜 미디어 모니터링 등에 활용됩니다.

**스키마:**
```json
{
  "text": "감성을 분석할 텍스트",
  "sentiment": "감성 라벨",
  "score": "신뢰도 점수 (선택적, 0-1 또는 1-5)"
}
```

`text` 필드는 분석 대상 텍스트이며, 주로 리뷰, 댓글, 트윗 등입니다. `sentiment`는 감정의 극성을 나타내는 라벨입니다. `score`는 감정의 강도나 신뢰도를 나타내며, 파인 그레인드(fine-grained) 분석에 유용합니다.

**train.jsonl 예시:**
```json
{"text": "이 제품 정말 최고예요! 완전 만족합니다.", "sentiment": "positive", "score": 5}
{"text": "배송이 느리고 포장도 엉망이었습니다. 실망스럽네요.", "sentiment": "negative", "score": 1}
{"text": "가격은 괜찮은데 기능이 아쉽습니다. 그럭저럭 쓸만해요.", "sentiment": "neutral", "score": 3}
{"text": "강력 추천합니다! 돈이 아깝지 않아요.", "sentiment": "positive", "score": 5}
{"text": "품질이 기대 이하입니다. 환불 요청했어요.", "sentiment": "negative", "score": 2}
{"text": "무난합니다. 특별히 좋지도 나쁘지도 않네요.", "sentiment": "neutral", "score": 3}
{"text": "서비스가 훌륭하고 직원들이 친절했습니다.", "sentiment": "positive", "score": 4}
```

감성 분석 데이터는 도메인 의존성이 높습니다. 영화 리뷰에서 학습한 모델을 제품 리뷰에 적용하면 성능이 떨어질 수 있습니다. 따라서 목표 도메인의 데이터를 충분히 확보하는 것이 중요합니다. 또한 중립적인 샘플도 적절히 포함하여 모델이 극단적 판단을 피하도록 해야 합니다.

## 4. 데이터 분할 전략

### 4.1. 파일명 기반 자동 분할

Hugging Face는 파일명에 포함된 키워드를 통해 자동으로 데이터를 스플릿으로 분할합니다. 이는 가장 간단하고 추천되는 방식이며, 별도의 설정 파일이나 코드 작성이 필요하지 않습니다.

**자동 인식 패턴:**

```
my_dataset/
├── train.jsonl          # 학습 데이터로 자동 인식
├── validation.jsonl     # 검증 데이터로 자동 인식
└── test.jsonl           # 테스트 데이터로 자동 인식
```

파일명에 스플릿 키워드가 포함되어 있으면 Hugging Face가 자동으로 해당 파일을 적절한 스플릿으로 할당합니다. 대소문자를 구분하지 않으므로 `Train.jsonl`도 학습 데이터로 인식됩니다.

**변형 가능한 파일명:**
- `train.jsonl`, `training.jsonl`, `train-data.jsonl` → train 스플릿
- `valid.jsonl`, `val.jsonl`, `dev.jsonl`, `validation.jsonl` → validation 스플릿
- `test.jsonl`, `testing.jsonl`, `eval.jsonl` → test 스플릿

**샤딩된 대용량 데이터:**

대용량 데이터셋은 여러 파일로 분할할 수 있으며, Hugging Face가 자동으로 병합합니다. 이는 메모리 제약이 있거나 병렬 처리를 원할 때 유용합니다.

```
my_dataset/
├── train-00000.jsonl    # 첫 번째 샤드
├── train-00001.jsonl    # 두 번째 샤드
├── train-00002.jsonl    # 세 번째 샤드
├── validation.jsonl
└── test.jsonl
```

샤딩된 파일은 숫자 접미사(suffix)를 사용하여 순서를 나타냅니다. Hugging Face는 `train-*` 패턴의 모든 파일을 찾아 하나의 train 스플릿으로 병합합니다. 샤드 간 순서는 파일명의 사전식(lexicographical) 순서를 따릅니다.

### 4.2. 폴더 기반 분할

서브디렉토리를 사용하여 스플릿을 구성할 수도 있습니다. 이 방식은 데이터 구조가 복잡하거나 메타데이터를 함께 관리해야 할 때 유용합니다.

```
my_dataset/
├── train/
│   ├── data.jsonl
│   └── metadata.json
├── validation/
│   ├── data.jsonl
│   └── metadata.json
└── test/
    ├── data.jsonl
    └── metadata.json
```

이 구조에서 각 폴더명(`train`, `validation`, `test`)이 스플릿 이름이 됩니다. 폴더 내부의 파일명은 임의로 지정할 수 있지만, 모든 폴더에서 동일한 파일명을 사용하는 것이 좋습니다. `metadata.json`은 해당 스플릿의 추가 정보를 저장하는 선택적 파일입니다.

**주의사항:** 폴더 기반 분할 시 각 폴더 내 데이터 파일명은 동일해야 하며, 폴더명이 스플릿 이름으로 사용됩니다. 로딩 시 `data_dir` 파라미터로 루트 디렉토리를 지정하면 자동으로 모든 서브디렉토리를 탐색합니다.

### 4.3. 분할 비율 가이드라인

데이터셋을 분할할 때는 태스크와 데이터 크기를 고려해야 합니다. 적절한 분할 비율은 모델의 학습 효율과 평가 신뢰도에 직접적인 영향을 미칩니다.

**일반적인 분할 비율:**

| 데이터셋 크기 | Train | Validation | Test |
|--------------|-------|------------|------|
| 소형 (1K-10K) | 70% | 15% | 15% |
| 중형 (10K-100K) | 80% | 10% | 10% |
| 대형 (100K+) | 85-90% | 5-10% | 5-10% |

소규모 데이터셋에서는 검증과 테스트에 충분한 샘플을 할당하여 평가의 통계적 유의성을 확보해야 합니다. 대규모 데이터셋에서는 학습 데이터의 비중을 높여 모델의 학습 능력을 최대화합니다. 검증 세트는 하이퍼파라미터 튜닝과 조기 종료(early stopping)에 사용되며, 테스트 세트는 최종 성능 평가에만 사용됩니다.

**크로스 밸리데이션 구조:**

K-Fold 크로스 밸리데이션(cross validation)을 위한 폴더 구조는 다음과 같습니다. 이 방법은 소규모 데이터셋에서 모델 성능을 더 신뢰성 있게 평가할 수 있습니다.

```
my_dataset/
├── fold_0/
│   ├── train.jsonl
│   └── validation.jsonl
├── fold_1/
│   ├── train.jsonl
│   └── validation.jsonl
├── fold_2/
│   ├── train.jsonl
│   └── validation.jsonl
├── fold_3/
│   ├── train.jsonl
│   └── validation.jsonl
├── fold_4/
│   ├── train.jsonl
│   └── validation.jsonl
└── test.jsonl
```

각 폴드(fold)는 전체 데이터를 다르게 분할한 버전입니다. K번의 학습을 수행하여 평균 성능을 계산하면 모델의 일반화(generalization) 능력을 더 정확히 파악할 수 있습니다. 테스트 세트는 모든 폴드에서 공통으로 사용됩니다.

## 5. 자동 로딩 설정

### 5.1. datasets.load_dataset() 사용법

Hugging Face의 `load_dataset()` 함수는 로컬 디렉토리나 Hugging Face Hub에서 데이터를 로딩합니다. 파일 구조와 명명 규칙만 올바르면 단 한 줄의 코드로 데이터를 로딩할 수 있습니다.

**기본 로딩 (로컬):**

데이터셋이 다음 구조로 구성되어 있다면:

```
./my_dataset/
├── train.jsonl
├── validation.jsonl
└── test.jsonl
```

별도의 설정 없이 로딩할 수 있습니다. `data_dir` 파라미터에 데이터셋 폴더 경로를 지정하면 됩니다.

**스플릿 접근:**

로딩된 데이터셋은 딕셔너리 형태로 각 스플릿에 접근할 수 있습니다. `dataset['train']`은 학습 데이터를, `dataset['validation']`은 검증 데이터를 반환합니다. 각 스플릿은 인덱싱, 슬라이싱(slicing), 이터레이션(iteration)을 지원합니다.

**특정 스플릿만 로딩:**

모든 스플릿이 필요하지 않을 때는 `split` 파라미터로 특정 스플릿만 로딩할 수 있습니다. 이는 메모리를 절약하고 로딩 시간을 단축합니다.

**다중 컨피규레이션 로딩:**

서브디렉토리 구조를 사용한 경우, 특정 컨피규레이션을 선택할 수 있습니다. `data_dir`에 원하는 서브디렉토리 경로를 지정하면 됩니다.

**스트리밍 모드:**

대용량 데이터셋은 스트리밍(streaming)으로 로딩하여 메모리를 절약할 수 있습니다. 스트리밍 모드에서는 데이터를 전부 메모리에 로드하지 않고, 필요할 때마다 디스크에서 읽어옵니다. 이는 수백 GB 크기의 데이터셋을 다룰 때 필수적입니다.

### 5.2. 데이터셋 카드 필수 요소

데이터셋 카드는 `README.md` 파일로 작성하며, 데이터셋의 목적, 구조, 사용법을 설명합니다. Hugging Face Hub에 업로드할 때 필수이며, 다른 연구자나 개발자가 데이터셋을 이해하고 사용하는 데 중요한 역할을 합니다.

**최소 템플릿:**

데이터셋 카드는 YAML 프론트매터와 마크다운 본문으로 구성됩니다. YAML 섹션은 메타데이터를 정의하고, 마크다운 섹션은 상세 설명을 제공합니다.

프론트매터에는 언어, 라이선스(license), 태스크 카테고리, 크기 범위 등의 메타데이터를 포함합니다. 이 정보는 Hugging Face Hub에서 데이터셋을 필터링하고 검색하는 데 사용됩니다.

본문에는 데이터셋의 개요, 지원 태스크, 데이터 필드 설명, 분할 통계, 생성 방법, 사용 시 고려사항, 인용 정보 등을 포함합니다. 명확하고 자세한 문서는 데이터셋의 활용도를 크게 높입니다.

### 5.3. 자동 인식되는 메타데이터

Hugging Face는 특정 파일과 메타데이터를 자동으로 인식합니다. 이러한 컨벤션을 따르면 추가 설정 없이도 데이터셋이 올바르게 동작합니다.

**자동 인식 파일:**
- `README.md`: 데이터셋 카드로 인식되며, Hub에서 자동 렌더링
- `dataset_infos.json`: 자동 생성되는 메타데이터 파일 (수동 편집 비추천)
- `.gitattributes`: Git LFS 설정 파일로, 대용량 파일 관리에 사용

**YAML 프론트매터:**

`README.md` 상단의 YAML 블록은 Hugging Face Hub에서 필터링과 검색에 사용됩니다. 주요 필드는 다음과 같습니다.

`language`: 데이터셋에 포함된 언어 목록입니다. ISO 639-1 코드를 사용하며, 다국어 데이터셋은 여러 언어를 리스트로 지정합니다.

`license`: 데이터셋의 라이선스입니다. `mit`, `apache-2.0`, `cc-by-4.0` 등 표준 라이선스 식별자를 사용합니다.

`task_categories`: 데이터셋이 지원하는 태스크입니다. `text-classification`, `text-generation`, `question-answering` 등의 표준 카테고리를 사용합니다.

`size_categories`: 데이터셋의 크기 범위입니다. `n<1K`, `1K<n<10K`, `10K<n<100K` 등의 형식을 사용합니다.

`tags`: 추가 키워드나 특성을 나타냅니다. `instruction-tuning`, `conversational`, `korean` 등 자유롭게 지정할 수 있습니다.

## 6. 검증 체크리스트

### 6.1. 필수 필드 확인

데이터셋을 로딩하기 전에 각 태스크에 필요한 필드가 모두 존재하는지 확인해야 합니다. 누락된 필드가 있으면 학습 중 오류가 발생하거나 모델이 제대로 학습되지 않을 수 있습니다.

**인스트럭션 튜닝:**
- ✅ `instruction` 필드 필수
- ✅ `output` 필드 필수
- ⚠️ `input` 필드 선택적 (없으면 빈 문자열로 처리)

**텍스트 분류:**
- ✅ `text` 필드 필수
- ✅ `label` 필드 필수
- ⚠️ 라벨이 일관된 형식인지 확인 (모두 문자열 또는 모두 정수)

**질의응답:**
- ✅ `context` 필드 필수
- ✅ `question` 필드 필수
- ✅ `answer` 필드 필수
- ⚠️ `answer_start` 필드는 추출형 QA에서 권장

**대화형:**
- ✅ `messages` 배열 필수
- ✅ 각 메시지는 `role`과 `content` 필드 포함
- ⚠️ 역할은 `user`와 `assistant`가 번갈아 나타나는 것이 일반적

필드 누락이나 오타는 데이터 로딩 단계에서 발견되지 않고 학습 중에 오류를 일으킬 수 있습니다. 따라서 데이터 생성 후 반드시 필드 존재 여부와 타입을 검증해야 합니다.

### 6.2. 인코딩 및 포맷 검증

**UTF-8 인코딩 확인:**

모든 텍스트 파일은 UTF-8로 인코딩되어야 합니다. 특히 한글, 한자, 이모지 등 유니코드 문자를 사용할 때 주의해야 합니다. 잘못된 인코딩은 문자 깨짐(mojibake)을 유발하며, 모델 학습에 악영향을 미칩니다.

UTF-8이 아닌 인코딩(예: EUC-KR, CP949)으로 저장된 파일은 변환이 필요합니다. 텍스트 에디터나 파일 변환 도구를 사용하여 UTF-8로 재저장할 수 있습니다.

**JSONL 포맷 검증:**

각 라인이 유효한 JSON인지 확인합니다. JSONL 파일에서 흔한 오류는 다음과 같습니다.

첫째, 마지막 줄에 불필요한 빈 줄이 있는 경우입니다. 빈 줄은 파싱 오류를 일으킬 수 있으므로 제거해야 합니다.

둘째, JSON 배열 형식으로 작성된 경우입니다. JSONL은 각 줄이 독립적인 JSON 객체여야 하며, 전체를 배열로 감싸면 안 됩니다.

셋째, 이스케이핑(escaping)되지 않은 특수 문자입니다. 큰따옴표, 백슬래시, 줄바꿈 문자 등은 JSON 규칙에 따라 이스케이핑되어야 합니다.

넷째, BOM(Byte Order Mark)이 포함된 경우입니다. UTF-8 BOM은 일부 시스템에서 문제를 일으킬 수 있으므로 제거하는 것이 좋습니다.

**공통 문제 해결:**

줄바꿈이 포함된 텍스트는 `\n`으로 이스케이핑해야 합니다. 큰따옴표는 `\"`로 이스케이핑합니다. 백슬래시는 `\\`로 이스케이핑합니다. JSON 문자열 내에서 탭은 `\t`로 표현합니다.

### 6.3. 로딩 테스트

실제로 Hugging Face로 로딩하여 문제가 없는지 확인합니다. 로딩 테스트는 데이터셋 배포 전 필수 단계입니다.

**확인 사항:**

첫째, 모든 스플릿이 올바르게 인식되었는가? `train`, `validation`, `test` 키가 모두 존재하는지 확인합니다.

둘째, 샘플 데이터가 예상한 구조인가? 첫 번째 샘플을 출력하여 필드명과 데이터 타입이 올바른지 검사합니다.

셋째, 필드명이 일관되게 유지되는가? 모든 샘플이 동일한 필드 세트를 가지는지 확인합니다.

넷째, 데이터 타입이 적절한가? 텍스트 필드는 문자열, 숫자 필드는 정수나 실수, 라벨은 일관된 타입이어야 합니다.

다섯째, 샘플 수가 예상과 일치하는가? 각 스플릿의 샘플 개수를 확인하여 데이터 손실이 없는지 검증합니다.

로딩 테스트를 통과하면 데이터셋을 실제 학습에 사용할 준비가 완료된 것입니다. 오류가 발생하면 에러 메시지를 주의 깊게 읽고, 파일 구조나 데이터 포맷을 수정한 후 다시 테스트합니다.

## 7. 즉시 사용 가능한 템플릿

### 7.1. 7가지 태스크별 완전한 예시

각 태스크에 대한 완전한 디렉토리 구조와 샘플 데이터를 제공합니다. 이 템플릿을 복사하여 자신의 데이터로 채우면 즉시 학습을 시작할 수 있습니다.

#### 7.1.1. 인스트럭션 튜닝 프로젝트

```
instruction_tuning_dataset/
├── train.jsonl          (8000 samples)
├── validation.jsonl     (1000 samples)
├── test.jsonl           (1000 samples)
└── README.md
```

**train.jsonl (5개 샘플):**
```jsonl
{"instruction": "다음 문장을 영어로 번역하세요.", "input": "인공지능이 우리의 삶을 변화시키고 있습니다.", "output": "Artificial intelligence is transforming our lives."}
{"instruction": "주어진 숫자들의 평균을 계산하세요.", "input": "10, 20, 30, 40, 50", "output": "평균은 30입니다. 계산 방법: (10+20+30+40+50)/5 = 30"}
```

4. 노이즈 제거: 의미 없는 문자나 HTML 태그 제거
5. 길이 필터링: 너무 짧거나 긴 샘플 제외
6. 프라이버시 보호: 개인정보, 민감 정보 익명화

### D. 일반적인 오류와 해결 방법

**오류 1: 파일을 찾을 수 없음**
- 원인: 파일 경로가 잘못되었거나 파일명이 틀림
- 해결: 경로와 파일명을 정확히 확인, 상대 경로 대신 절대 경로 사용

**오류 2: JSON 파싱 실패**
- 원인: JSONL 포맷이 올바르지 않음
- 해결: 각 줄이 완전한 JSON 객체인지 확인, 이스케이핑 점검

**오류 3: 인코딩 오류**
- 원인: UTF-8이 아닌 다른 인코딩으로 저장됨
- 해결: 파일을 UTF-8로 재저장, BOM 제거

**오류 4: 메모리 부족**
- 원인: 데이터셋이 메모리보다 큼
- 해결: 스트리밍 모드 사용, 데이터 샤딩, 배치 크기 감소

**오류 5: 필드 누락**
- 원인: 일부 샘플에 필수 필드가 없음
- 해결: 모든 샘플의 스키마 일관성 확인, 누락 필드 추가

### E. 성능 최적화 전략

**로딩 속도 향상:**

1. Parquet 포맷 사용: JSONL보다 빠른 로딩 속도
2. 데이터 샤딩: 병렬 로딩 가능
3. 캐싱 활용: 한 번 로딩한 데이터 재사용
4. 스트리밍 모드: 대용량 데이터에 효과적

**학습 효율 개선:**

1. 적절한 배치 크기 선택
2. 데이터 증강으로 다양성 확보
3. 클래스 밸런싱으로 편향 감소
4. 검증 세트로 조기 종료 적용

**저장 공간 절약:**

1. 압축 포맷 사용 (Parquet, gzip)
2. 불필요한 필드 제거
3. 토큰화 후 정수 인덱스로 저장
4. Git LFS로 대용량 파일 관리

이 가이드는 Hugging Face 에코시스템에서 LLM 파인튜닝을 위한 데이터셋을 구성하는 실용적인 방법을 제시했습니다. 핵심은 **컨벤션을 따르는 것**입니다. 파일 명명 규칙과 폴더 구조만 올바르게 설정하면 복잡한 코딩 없이도 전문적인 데이터셋을 만들 수 있습니다.

### 핵심 원칙 요약

**1. 표준을 따르세요**

파일명에 `train`, `validation`, `test` 키워드를 포함하면 Hugging Face가 자동으로 인식합니다. JSONL 포맷에서 각 줄은 하나의 완전한 JSON 객체여야 합니다. UTF-8 인코딩은 필수이며, 한글과 특수문자를 안전하게 처리합니다.

**2. 일관성을 유지하세요**

모든 샘플이 동일한 필드 구조를 가져야 합니다. 라벨 형식을 통일하고, 데이터 타입을 일관되게 유지하세요. README 문서로 데이터셋 구조를 명확히 설명하세요.

**3. 품질에 투자하세요**

데이터는 모델 성능의 상한선을 결정합니다. 중복을 제거하고, 오류를 수정하며, 편향을 최소화하세요. 어노테이션 품질을 높이기 위해 가이드라인을 만들고 검증 프로세스를 구축하세요.

**4. 검증을 생활화하세요**

데이터를 만든 후 반드시 로딩 테스트를 수행하세요. 필드 존재 여부, 인코딩, JSON 포맷을 확인하세요. 샘플 몇 개를 직접 확인하여 데이터의 품질을 점검하세요.

**5. 문서화하세요**

좋은 README는 데이터셋의 가치를 높입니다. 데이터 출처, 수집 방법, 라이선스, 사용법을 명확히 기록하세요. 다른 사람이 쉽게 이해하고 사용할 수 있도록 예시를 제공하세요.

### 다음 단계

데이터셋 구성이 완료되었다면 다음 단계를 진행하세요.

**단계 1: 품질 검증**

전체 데이터셋을 스캔하여 일관성을 확인하세요. 샘플을 랜덤으로 추출하여 수동 검토하세요. 클래스 분포를 확인하여 불균형이 없는지 점검하세요.

**단계 2: 로딩 테스트**

Hugging Face datasets 라이브러리로 로딩을 시도하세요. 각 스플릿의 샘플 수를 확인하세요. 첫 번째 샘플을 출력하여 구조를 검증하세요.

**단계 3: 파인튜닝 시작**

사전학습된 모델을 선택하세요. Transformers 라이브러리의 Trainer를 활용하세요. 작은 배치로 먼저 테스트하여 문제가 없는지 확인하세요.

**단계 4: 성능 평가**

검증 세트로 하이퍼파라미터를 튜닝하세요. 테스트 세트로 최종 성능을 측정하세요. 오류 분석을 수행하여 개선점을 찾으세요.

**단계 5: 반복 개선**

성능이 낮은 샘플을 분석하세요. 데이터 증강이나 추가 수집을 고려하세요. 모델과 데이터를 함께 개선하는 사이클을 반복하세요.

### 커뮤니티 기여

좋은 데이터셋을 만들었다면 Hugging Face Hub에 공유하는 것을 고려하세요. 오픈소스 커뮤니티는 공유를 통해 성장합니다. 여러분의 데이터셋이 다른 연구자나 개발자에게 영감을 줄 수 있습니다.

데이터셋을 공개할 때는 라이선스를 명확히 하고, 프라이버시를 보호하며, 윤리적 고려사항을 문서화하세요. 사용자들의 피드백을 받아 지속적으로 개선하세요.

### 계속 학습하기

NLP와 LLM 분야는 빠르게 발전하고 있습니다. 최신 논문을 읽고, 새로운 기법을 시도하며, 커뮤니티와 교류하세요. Hugging Face 포럼, Reddit의 r/MachineLearning, Papers with Code 등이 좋은 리소스입니다.

데이터는 AI의 연료입니다. 잘 구성된 데이터셋은 모델 성능의 기반이며, 반복적인 실험과 개선의 출발점입니다. 이 가이드가 여러분의 AI 프로젝트에 도움이 되기를 바랍니다.
