## 1\. Streamlit을 활용한 AI 모델 웹 애플리케이션 통합 단계 설명

Streamlit은 데이터 과학자와 머신러닝 엔지니어가 복잡한 웹 개발 지식 없이도 빠르게 대화형 웹 애플리케이션을 구축할 수 있도록 돕는 파이썬 라이브러리입니다. AI 모델을 웹 애플리케이션에 통합하는 과정은 크게 **모델 로드 (Model Loading)**, **사용자 입력 (User Input)**, \*\*결과 출력 (Result Output)\*\*의 세 단계로 나눌 수 있습니다.

### 1.1. 모델 로드 (Model Loading)

이 단계는 **AI 모델이 웹 애플리케이션에서 사용할 수 있도록 메모리에 올리는 과정**입니다.

  * **1.1.1. 목적 및 필요성:**

      * AI 모델은 일반적으로 학습된 가중치(weights)와 구조(architecture)를 포함하는 파일 형태로 저장되어 있습니다 (예: `.pth`, `.h5`, `.pkl` 파일). 이 파일을 읽어와서 파이썬 객체로 변환해야 추론(Inference)을 수행할 수 있습니다.
      * 웹 애플리케이션이 실행될 때마다 모델을 매번 로드하면 시간이 오래 걸리고 비효율적이므로, **최초 1회만 로드하여 메모리에 캐시(Cache)하는 것이 중요**합니다.

  * **1.1.2. Streamlit에서의 구현:**

      * Streamlit에서는 `st.cache_resource` (구 `st.experimental_singleton`) 데코레이터를 사용하여 모델 로드 함수를 감싸는 것이 일반적입니다.
      * 이 데코레이터를 사용하면, 애플리케이션이 다시 실행되거나 사용자가 상호작용할 때 **모델 로드 함수가 다시 호출되는 것을 방지**하고, 모델 객체를 메모리에 유지하여 성능을 최적화합니다.
      * **예시 코드 구조:**

        ```python
        # 모델 로딩 함수
        @st.cache_resource 
        def load_ai_model():
            # 모델 파일 로드 및 초기화 로직

            return loaded_model

        model = load_ai_model() # 애플리케이션 시작 시 단 1회만 실행됨
        ```

### 1.2. 사용자 입력 (User Input)

이 단계는 **AI 모델이 추론을 수행하는 데 필요한 데이터를 사용자로부터 받는 과정**입니다.

  * **1.2.1. 목적 및 필요성:**

      * AI 모델의 입력 형태(텍스트, 이미지, 숫자 등)에 맞게 사용자가 데이터를 제공할 수 있는 인터페이스(Interface)를 제공해야 합니다.
      * 입력 데이터는 모델이 요구하는 형식(데이터 타입, 차원 등)에 맞게 \*\*전처리(Preprocessing)\*\*되는 과정을 거쳐야 합니다.

  * **1.2.2. Streamlit에서의 구현:**

      * Streamlit은 다양한 위젯(Widgets)을 제공하여 사용자 입력을 쉽게 받을 수 있습니다.
          * **텍스트 입력:** `st.text_input`, `st.text_area`
          * **숫자 입력:** `st.number_input`, `st.slider`
          * **파일 업로드:** `st.file_uploader` (이미지, CSV, 텍스트 파일 등)
          * **버튼:** `st.button` (추론 실행 트리거)
      * **입력 처리 로직:**
        1.  사용자가 위젯을 통해 데이터 입력.
        2.  `st.button` 등을 클릭하여 추론 실행을 요청.
        3.  입력된 데이터를 모델의 요구사항에 맞게 변환 (예: 이미지 리사이즈 및 텐서 변환, 텍스트 토큰화).

### 1.3. 결과 출력 (Result Output)

이 단계는 **AI 모델의 추론 결과를 사용자에게 시각적으로 이해하기 쉽도록 보여주는 과정**입니다.

  * **1.3.1. 목적 및 필요성:**

      * AI 모델의 출력(예: 분류 클래스, 예측값, 생성된 이미지)은 종종 원시 데이터 형태(raw data)이므로, 사용자가 이해할 수 있는 형태로 \*\*후처리(Postprocessing)\*\*하여 제시해야 합니다.
      * 결과를 효과적으로 전달하기 위해 텍스트뿐만 아니라 차트, 이미지, 표 등의 시각화 요소를 활용하는 것이 좋습니다.

  * **1.3.2. Streamlit에서의 구현:**

      * Streamlit은 결과를 표시하기 위한 다양한 출력 함수를 제공합니다.
          * **텍스트 출력:** `st.write`, `st.text`, `st.success`, `st.error`
          * **데이터 출력:** `st.dataframe`, `st.table`
          * **차트/시각화:** `st.line_chart`, `st.bar_chart`, `st.pyplot` (Matplotlib), `st.altair_chart`
          * **이미지 출력:** `st.image`
      * **전체적인 추론 및 출력 과정:**
        1.  사용자 입력 데이터를 전처리.
        2.  전처리된 데이터를 로드된 모델(`model`)에 입력하여 추론(`model.predict(processed_input)`).
        3.  모델 출력 결과를 후처리 (예: 확률을 클래스 레이블로 변환, bounding box 좌표 시각화).
        4.  Streamlit 출력 함수를 사용하여 결과를 웹 페이지에 표시.

## 2\. FastAPI를 활용한 AI 모델 웹 API 서버 코드 구조

FastAPI는 비동기(asynchronous) 처리가 가능하고 높은 성능을 제공하는 파이썬 웹 프레임워크로, AI 모델을 통합하는 백엔드 API 서버를 구축하는 데 매우 적합합니다. 기능별로 코드를 분리하여 구성하는 것은 유지보수성(Maintainability), 확장성(Scalability), 그리고 코드의 가독성(Readability)을 높이는 데 필수적입니다.

다음은 AI 모델 API 서버를 구현할 때 바람직한 프로젝트 디렉토리 구조와 각 파일의 역할에 대한 설명입니다.

### 2.1. 권장되는 디렉토리 구조 (Directory Structure)

```
/ai_api_server
├── main.py                    # 1. 메인 애플리케이션 파일 (FastAPI 인스턴스, 서버 실행)
├── /app/
│   ├── __init__.py            
│   ├── /models/               # 2. AI 모델 및 로직 (핵심 추론 기능)
│   │   ├── ai_model.py        #    - AI 모델 로드, 전/후처리 로직, 추론 함수 포함
│   │   ├── __init__.py        
│   │   └── config.py          #    - 모델 경로, 하이퍼파라미터 등 설정
│   ├── /schemas/              # 3. 데이터 유효성 검사 및 응답 구조 (Pydantic)
│   │   ├── request_schemas.py #    - API 요청 데이터(입력) 형식 정의 (예: InputData)
│   │   ├── response_schemas.py#    - API 응답 데이터(출력) 형식 정의 (예: ResultData)
│   │   └── __init__.py
│   ├── /api/                  # 4. API 라우터 (Endpoints)
│   │   ├── routers.py         #    - API 엔드포인트 정의 및 요청 처리 (주요 라우터)
│   │   └── __init__.py
│   └── /core/                 # 5. 핵심 유틸리티 및 설정
│       ├── config.py          #    - 환경 변수, 기본 설정값 등
│       ├── exceptions.py      #    - 커스텀 예외 처리
│       └── utils.py           #    - 기타 공통 유틸리티 함수 (로깅, 파일 처리 등)
├── Dockerfile                 # 6. 도커 빌드 파일
├── requirements.txt           # 7. 파이썬 의존성 리스트
└── .env                       # 8. 환경 변수 파일 (선택적)
```

### 2.2. 주요 구성 요소별 설명

#### 2.2.1. `main.py` (메인 애플리케이션)

  * **역할:** FastAPI 애플리케이션의 진입점(Entry Point).
  * **포함 내용:** `FastAPI()` 인스턴스 생성, CORS/미들웨어 설정, 그리고 `/app/api/routers.py`에 정의된 라우터들을 애플리케이션에 포함(`app.include_router()`).

#### 2.2.2. `/app/models/` (AI 모델 및 비즈니스 로직)

  * **역할:** AI 모델의 로딩, 전처리, 추론, 후처리 등 **핵심 로직**을 담당합니다.
  * `ai_model.py`:
      * **모델 로드:** 서버 시작 시 모델을 메모리에 **싱글턴(Singleton)** 패턴 또는 글로벌 객체로 한 번만 로드합니다.
      * **추론 함수:** 사용자 요청 데이터를 받아 모델에 전달하고 결과를 반환하는 함수를 포함합니다.

#### 2.2.3. `/app/schemas/` (데이터 모델 - Pydantic)

  * **역할:** API 요청 및 응답 데이터의 구조와 타입을 정의하여 데이터의 유효성을 검사합니다.
  * `request_schemas.py`: 클라이언트로부터 들어오는 데이터(JSON)의 형태를 Pydantic 클래스로 정의합니다 (예: 이미지 URL, 텍스트 입력).
  * `response_schemas.py`: 클라이언트로 나가는 응답 데이터의 형태를 정의하여 일관된 API 응답 구조를 유지합니다.

#### 2.2.4. `/app/api/` (API 라우터 - 엔드포인트 정의)

  * **역할:** 실제 API 엔드포인트(Endpoint)를 정의하고, 들어온 요청을 처리하며, `/app/models/`의 비즈니스 로직을 호출합니다.
  * `routers.py`: `APIRouter` 인스턴스를 사용하여 기능별로 엔드포인트를 그룹화하고, HTTP 메소드(GET, POST 등)와 경로를 매핑합니다.
      * **예시:** `/predict` 엔드포인트는 사용자 요청을 받아서, `request_schemas`로 유효성 검사를 하고, `ai_model.py`의 추론 함수를 호출한 후, 결과를 `response_schemas` 형태로 반환합니다.

#### 2.2.5. `/app/core/` (핵심 유틸리티 및 설정)

  * **역할:** 애플리케이션 전반에 걸쳐 사용되는 설정 및 보조 기능들을 관리합니다.
  * `config.py`: 환경 변수(Environment Variables)를 로드하고 관리하여, 환경에 따라 다른 설정을 적용할 수 있도록 합니다.

이러한 구조는 **관심사의 분리(Separation of Concerns)** 원칙을 따르므로, 모델 로직이 변경되더라도 API 엔드포인트 정의 파일은 거의 수정할 필요가 없으며, 데이터 형식이 바뀌면 `schemas` 파일만 수정하면 됩니다. 이는 대규모 AI 서비스 개발 및 팀 협업에 있어 매우 중요한 기반이 됩니다.

## 3. 가상 AI 서비스 아키텍처 설계: "VisionTune"

AI 엔지니어링의 최종 목표는 학습된 모델을 실제 사용자에게 서비스하는 것입니다. 이제 현존하는 기술 스택을 활용하여 가상의 AI 웹 서비스를 설계해 보겠습니다.

### 3.1. 선정된 AI 서비스: VisionTune (실시간 이미지 스타일 변환 서비스)

* **서비스 개요:** 사용자가 이미지를 업로드하면, 지정된 아티스트의 스타일(예: 고흐, 모네)로 실시간으로 변환하여 제공하는 서비스입니다 (Neural Style Transfer, 신경망 스타일 변환 기반).
* **주요 특징:**
    * **고부하:** 이미지 처리 및 딥러닝 추론은 CPU/GPU 자원을 많이 소모합니다.
    * **빠른 응답 속도 요구:** 사용자는 실시간 변환 결과를 기대합니다.

### 3.2. 전체 아키텍처 다이어그램 및 구성 요소

#### 3.2.1. 기술 스택 요약

| 구성 요소 | 기술 스택 | 역할 |
| :--- | :--- | :--- |
| **프론트엔드/데모** | Streamlit | 빠르고 쉽게 구축된 웹 인터페이스 및 관리용 대시보드 |
| **API 서버** | FastAPI (w/ Uvicorn) | 고성능 비동기 API 서버, 모델 추론 요청 처리 |
| **추론 최적화** | ONNX Runtime | 모델 추론 속도 및 효율성 극대화 |
| **컨테이너화** | Docker | 개발/배포 환경의 일관성 및 이식성 보장 |
| **클라우드** | AWS (Amazon Web Services) | 인프라 제공 및 확장성 지원 |
| **요청 처리** | Redis (대기 큐) | 고부하 요청 부하 분산 및 비동기 처리 |


#### 3.2.2. 클라우드 배포 구조 (AWS 기준)

| 레이어 | AWS 서비스 | 역할 설명 |
| :--- | :--- | :--- |
| **네트워크** | Amazon VPC, Route 53 | 안전한 사설 네트워크 구성 및 도메인 관리 |
| **로드 밸런싱** | AWS Application Load Balancer (ALB) | 프론트엔드 (Streamlit) 및 API 서버 (FastAPI)로 요청 분산 |
| **컴퓨팅** | Amazon ECS (Fargate) 또는 EKS | **Docker 컨테이너** 배포 및 관리. 특히, GPU 추론이 필요하면 **EC2 (w/ GPU)**를 사용하고 ECS/EKS로 관리 |
| **데이터베이스** | Amazon RDS, S3 | 사용자 데이터 및 변환된 이미지 저장 (S3) |

### 3.3. 핵심 기능별 구현 전략

#### 3.3.1. 추론 최적화 (Inference Optimization)

* **모델 경량화:** Neural Style Transfer 모델을 **ONNX (Open Neural Network Exchange)** 형식으로 변환합니다.
* **추론 엔진:** FastAPI 서버 내에서 **ONNX Runtime**을 사용하여 추론을 수행합니다. 이는 PyTorch나 TensorFlow의 기본 추론 엔진보다 더 빠르고 효율적인 CPU/GPU 활용을 가능하게 합니다.
* **배치 처리:** 멀티유저 요청을 한 번에 처리하기 위해, 일정 시간 동안 들어온 요청을 모아 **마이크로 배치(Micro-batching)** 단위로 묶어 추론을 수행합니다.

#### 3.3.2. 멀티유저 요청 처리 방안 (고성능 및 비동기)

VisionTune은 고부하 작업이므로, 비동기 처리가 필수입니다.

* **비동기 API:** FastAPI는 기본적으로 **async/await**를 지원하여 I/O 바운드 작업에 효율적입니다. 하지만 AI 추론은 CPU 바운드 작업이므로, **`run_in_threadpool`**을 사용하여 추론 함수를 별도의 스레드에서 실행하여 FastAPI의 메인 이벤트 루프를 블로킹(Blocking)하지 않도록 합니다.
* **대기 큐 (Waiting Queue):**
    1.  클라이언트가 FastAPI의 `/submit` 엔드포인트에 이미지와 스타일을 요청합니다.
    2.  FastAPI는 요청을 즉시 처리하는 대신, 요청 정보와 고유 ID를 생성하여 **Redis (또는 Kafka/SQS)** 대기 큐에 넣고, 클라이언트에게 **JobID**를 반환합니다.
    3.  별도의 **Worker 프로세스 (ECS/EKS에서 실행)**가 큐에서 작업을 가져와 (FastAPI 서버와 분리) 실제 고부하 추론을 수행합니다.
    4.  결과가 나오면 Worker는 결과를 S3에 저장하고, JobID와 함께 결과 준비 완료를 알립니다.
    5.  클라이언트는 주기적으로 `/status/{job_id}` 엔드포인트에 결과를 **폴링(Polling)**하여 결과를 가져옵니다.

### 3.4. 보안 및 모니터링/로깅 전략

#### 3.4.1. 보안 요소

* **CORS (Cross-Origin Resource Sharing):** `main.py` 파일에서 FastAPI의 `CORSMiddleware`를 사용하여, Streamlit 프론트엔드 도메인이나 허용된 도메인만 API에 접근할 수 있도록 제한합니다.
* **API Key 인증:** 주요 API 엔드포인트 (`/submit`)에 대해 **API Key**를 요구하고, 이를 AWS Secrets Manager 등에 안전하게 저장하여 검증합니다.
* **입력 유효성 검사:** Pydantic `schemas`를 사용하여 요청 데이터가 정의된 형식과 제약 조건(예: 이미지 파일 크기 제한)을 만족하는지 확인합니다.

#### 3.4.2. 모니터링 및 로깅 전략

* **로깅 (Logging):**
    * FastAPI와 Worker 프로세스에서 발생한 모든 로그를 JSON 포맷으로 표준 출력 (stdout)에 기록합니다.
    * Docker 컨테이너의 표준 출력 로그는 AWS CloudWatch Logs (또는 Elasticsearch, Fluentd, Kibana/ELK 스택)로 수집됩니다.
* **모니터링 (Monitoring):**
    * **AWS CloudWatch:** 서버의 CPU/메모리 사용률, 네트워크 트래픽 등 인프라 지표를 모니터링합니다.
    * **Prometheus & Grafana:** FastAPI 서버 내부에 **Prometheus Metric**을 노출하여, 추론 시간, 요청 지연 시간, 큐 길이 등 **애플리케이션 성능 지표**를 실시간으로 수집하고 Grafana 대시보드에서 시각화합니다.
    * **알림:** 특정 임계치(예: 에러 비율 1% 초과, 큐 길이 100 초과) 발생 시 알림 (SNS/Slack)을 설정하여 엔지니어에게 통보합니다.
